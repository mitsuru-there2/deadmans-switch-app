## 生存確認リマインドの役割分担（2026-10-24）

日常のリマインドはアプリが `expo-notifications` で端末OSに予約するローカル通知とする。サーバーから日次リマインドPushは送らない。アプリが取得した最新のサーバー状態が `active` / `grace` で有効契約があり、OS通知許可と端末内の有効設定がある場合に、24時間ごとの繰り返し通知を1件予約する。EAS projectId、Expo Push Token、`POST /v1/devices` はローカル通知の前提条件ではない。

- 有効化後とチェックイン成功後に状態を再取得し、最後のサーバー確認時刻が変わったら予約を更新する。同じ確認時刻の再取得だけでは通知時刻を先送りしない。端末内設定からの有効化・停止も提供する。
- `draft` / `paused` / `held` / `released`、契約失効、認証失効、復元による認証変更をアプリが確認した場合は、自アプリのリマインド予約を取り消す。ほかの用途の通知予約には触れない。
- ローカル通知への明示的タップは `kind:"notification_action"`、通常の本人操作による前面起動は `kind:"foreground"` として `POST /v1/check-ins` を呼ぶ。必要な端末ロック解除と前面状態の再検証を行う。通知の受信・表示では送らず、古いオフライン操作もバックグラウンド再送しない。成功応答前は未確定とする。
- チェックイン受付・受信時刻の記録・無反応期限監視・警告メール・警告受付後の猶予・公開判断はサーバーに残す。通知予約・表示をサーバーでの本人確認や警告メール受付の代わりにしない。
- サーバーCronは旧 `reminder` を新規作成しない。Outbox配信処理は旧 `reminder` の未送信レコードを、予定日時によらず取消・payload消去する。既に送信処理中の旧Pushの取消は保証しない。DB enum、`lastReminderAt`、端末管理APIは互換維持用で、ローカル通知の状態を表さない。DBマイグレーションは不要。

ローカル通知の停止は端末が状態を同期できた時点で反映する。別端末での停止や契約失効を、通信していない端末の予約へ即時反映する保証はない。通知文には本文・宛先・送信予定日の断定を含めない。OS通知設定、省電力などにより表示・正確な時刻は保証しない。Androidの正確なアラーム権限は追加せず、OSの通常の予約を使う。アプリ内でリマインドを止めてもサーバー監視は停止しない。

実機でのiOS/Android通知表示、再起動、省電力・権限変更、コールド起動タップの最終確認は別途必要です。ローカル検証はOS配信の保証を意味しません。
